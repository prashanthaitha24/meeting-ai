Security reviews and compliance

Security questionnaires, threat models, least-privilege IAM, data residency, audit logs and passing a customer's review.

Intermediate to advanced ~45 min read Module 15 of 20
Lesson Practice Cheat sheet Quiz

Almost every enterprise deployment passes through the customer's security review, and many pilots stall there, not because the software is unsafe but because nobody prepared clear answers. As an FDE you are often the person who can explain exactly what data flows where, who can access it and how it is protected. This lesson covers how security reviews work, the documents that speed them up, drawing data-flow diagrams and threat models, least-privilege access, the controls reviewers always ask about, and the AI-specific questions that now appear in every review.

After this module you can
  • Explain the stages of a customer security review and what reviewers need
  • Draw a data-flow diagram and run a lightweight STRIDE threat model
  • Design least-privilege access for people, services and cloud resources
  • Answer the standard control questions on encryption, secrets, logging and vulnerabilities
  • Address AI-specific concerns: data use, retention, prompt injection and output risk

How security reviews work

Reviews usually run in stages. A vendor assessment checks your company: questionnaires, compliance reports such as SOC 2 Type II or ISO 27001 certificates, penetration test summaries, policies. A solution review examines this specific deployment: architecture, data flows, access, where data is stored and processed. Some customers add a penetration test of the deployed system before production. Legal and privacy teams in parallel review the data processing agreement and any cross-border data transfers.

Book the review in the first week of the pilot, because security teams schedule weeks ahead. Your company's security or trust team usually owns the vendor assessment; you own the solution-specific answers. Prepare them before the first meeting, and keep a reusable pack that improves with every customer.

Data flows and threat models

The single most useful artefact is a data-flow diagram: every component, every arrow labelled with what data moves, over which protocol, authenticated how, and every place data is stored, with the trust boundaries (customer network, your cloud, a model provider) drawn explicitly. Reviewers think in flows; a clear diagram answers half their questions before they ask.

Then run a lightweight STRIDE threat model over the diagram: for each component and flow, ask about Spoofing (can someone pretend to be a user or service?), Tampering (can data be altered?), Repudiation (can actions be denied for lack of logs?), Information disclosure (can data leak?), Denial of service (can it be overwhelmed?) and Elevation of privilege (can someone gain more access?). Record each threat with its mitigation; reviewers trust teams who found their own risks first.

Least privilege everywhere

Reviewers look for the smallest possible access for each identity: people get roles mapped from the customer's groups, services get their own identities with only the permissions they use, and nothing uses shared or personal credentials. In cloud accounts, scope policies to specific actions and resources.

A narrowly scoped cloud policy: read one bucket prefix, nothing else
json
{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Sid": "ReadPolicyDocuments",
      "Effect": "Allow",
      "Action": ["s3:GetObject"],
      "Resource": "arn:aws:s3:::acme-policies/motor/*"
    },
    {
      "Sid": "ListOnlyThatPrefix",
      "Effect": "Allow",
      "Action": ["s3:ListBucket"],
      "Resource": "arn:aws:s3:::acme-policies",
      "Condition": {"StringLike": {"s3:prefix": ["motor/*"]}}
    }
  ]
}
  • Prefer workload identity (cloud roles bound to the Kubernetes service account) over long-lived keys.
  • Separate read and write identities; most FDE integrations only need read.
  • Time-bound human access for support, approved and logged, removed when the engagement ends.

The controls reviewers always ask about

AreaTypical questionGood answer includes
EncryptionIs data encrypted in transit and at rest?TLS versions, at-rest encryption and who holds keys
SecretsHow are credentials stored and rotated?Vault or cloud secret manager, rotation period, no secrets in code
LoggingWhat is logged, where, for how long?Audit events, no sensitive content, retention, customer access
VulnerabilitiesHow do you find and fix vulnerabilities?Image scanning, dependency updates, patch timelines by severity
Data residencyWhere is data stored and processed?Regions, sub-processors, no transfers without approval
DeletionHow is data deleted at the end?Process, timeline, written confirmation
IncidentsHow will you tell us about a breach?Notification timeline and contacts

Answer precisely and honestly. "Yes, AES-256 at rest with customer-managed keys in your KMS" beats "industry-standard encryption". If a control is missing, say so and propose a mitigation or a date; reviewers respect candour far more than vague assurance.

AI-specific questions

  • Training on our data: Is customer data used to train or improve any model? Have the contractual answer from each model provider and your own company ready.
  • Retention at the model provider: Are prompts and outputs stored, for how long, where? Zero-retention or in-tenant deployments may be required.
  • Where inference runs: hosted API, the customer's cloud tenancy, or self-hosted inside their network.
  • Access control in retrieval: How do you prevent users seeing documents they are not entitled to? (Permission-filtered retrieval, as in the LLM apps lesson.)
  • Prompt injection and actions: What stops malicious content from causing harmful actions? (Validation, least-privilege tools, human approval.)
  • Output risk: How are hallucinations, bias and harmful outputs detected and handled? (Evaluation, citations, human review, feedback channel.)
  • Logging of prompts: Are prompts logged? Who can see them? (Ideally metadata only by default.)
Tip

Turn each answered review into reusable material: an up-to-date architecture and data-flow diagram, a standard answers document, and a list of configuration options (in-tenant models, no prompt logging, customer-managed keys) that resolve common objections.

Hands-on practice

Prepare a security review pack

  1. Take the RAG assistant or support agent you built in stage 3 and draw its data-flow diagram with trust boundaries.
  2. Fill a flow table: data, protocol, authentication, storage and retention for every arrow.
  3. Run STRIDE over the diagram and write at least eight threats with mitigations.
  4. Write least-privilege policies for each service identity (cloud policy or Kubernetes RBAC).
  5. Answer the seven standard control questions and the seven AI-specific questions in writing, precisely.
  6. Ask a colleague to play the reviewer, question you for 30 minutes, and record every question you could not answer.
Cheat sheet

Security reviews and compliance — at a glance

Main things to focus on

  • Book the security review in week one; prepare answers before the meeting.
  • A data-flow diagram with trust boundaries answers most questions.
  • STRIDE your own design and show mitigations.
  • Least privilege for people, services and cloud resources; no shared credentials.
  • Precise, honest answers; propose mitigations for gaps.
  • Have clear answers on training use, retention, inference location and prompt injection.

Common pitfalls

  • Booking the security review after the build is finished.
  • Vague answers such as 'industry-standard security'.
  • Service accounts with broad or administrator permissions.
  • Not knowing whether the model provider retains or trains on prompts.
  • Logging full prompts and answers by default.
