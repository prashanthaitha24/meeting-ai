Networks and security at customer sites

Proxies, firewalls, DNS, TLS and private CAs, VPNs and SSO: why things that work on your laptop fail inside an enterprise.

Beginner ~40 min read Module 4 of 20
Lesson Practice Cheat sheet Quiz

The most common FDE day-one failure has nothing to do with your code: the software that ran perfectly in your cloud account cannot reach anything inside the customer's network. Enterprises route traffic through proxies, inspect TLS with their own certificate authorities, allow outbound traffic only to approved destinations, split DNS between inside and outside, and put everything behind single sign-on. This lesson explains each of those layers, how to diagnose which one is blocking you, and how to configure software, containers and Kubernetes to work with them rather than around them.

After this module you can
  • Configure applications and containers for explicit HTTP proxies and NO_PROXY
  • Diagnose TLS failures caused by inspecting proxies and private certificate authorities
  • Request the right firewall and egress allowlist changes with precise details
  • Reach internal systems through jump hosts and VPNs safely
  • Explain how SSO with OIDC or SAML fits into an application you deploy

Proxies: the gate in front of the internet

Many enterprises do not let servers talk to the internet directly. Outbound HTTP and HTTPS must go through an explicit proxy: the client connects to the proxy and, for HTTPS, asks it to open a tunnel with the HTTP CONNECT method. Most tools read the conventional environment variables HTTP_PROXY, HTTPS_PROXY and NO_PROXY (some only the lowercase forms), and requests to internal hosts must be excluded through NO_PROXY or they will be sent to the proxy, which cannot reach them.

Proxy settings for a shell and a test through them
bash
export HTTPS_PROXY=http://proxy.corp.example:8080
export HTTP_PROXY=http://proxy.corp.example:8080
export NO_PROXY=localhost,127.0.0.1,.corp.example,10.0.0.0/8,.svc,.cluster.local
export https_proxy=$HTTPS_PROXY http_proxy=$HTTP_PROXY no_proxy=$NO_PROXY

curl -sv https://pypi.org/simple/ -o /dev/null 2>&1 | grep -E 'proxy|CONNECT|HTTP/'
  • NO_PROXY syntax varies by tool: suffixes like .corp.example are widely understood, CIDR ranges are not supported everywhere. Test each tool you rely on.
  • The Docker daemon needs its own proxy configuration to pull images; containers do not inherit the host's shell variables, so pass them explicitly.
  • In Kubernetes, include the cluster's service and pod domains (.svc, .cluster.local) and CIDRs in NO_PROXY, or in-cluster calls will be sent to the proxy and fail.

TLS inspection and private certificate authorities

Many corporate proxies inspect TLS: they terminate your HTTPS connection, examine it, and re-encrypt it with a certificate signed by the company's own certificate authority (CA). Company laptops trust that CA; your container image does not. The symptom is a certificate verification error such as "self-signed certificate in certificate chain" or "unable to get local issuer certificate" for sites that are perfectly valid outside. Internal services are often signed by a private CA too.

See who actually signed the certificate you receive
bash
openssl s_client -connect api.github.com:443 -servername api.github.com \
  -showcerts </dev/null 2>/dev/null | grep -E 's:|i:'
# issuer 'i:' shows the corporate CA instead of a public one when a proxy inspects TLS

The fix is to trust the customer's CA, never to turn verification off. Get the CA certificate (PEM) from the customer's security team, add it to the system trust store (update-ca-certificates on Debian-style systems, update-ca-trust on Red Hat-style), and make sure each runtime uses it: Python with httpx and OpenSSL honours SSL_CERT_FILE, the requests library uses REQUESTS_CA_BUNDLE, Node.js uses NODE_EXTRA_CA_CERTS, and Java needs the CA imported into its truststore.

Bake the customer CA into an image (or mount it at runtime)
dockerfile
FROM python:3.12-slim
COPY customer-root-ca.pem /usr/local/share/ca-certificates/customer-root-ca.crt
RUN update-ca-certificates
ENV SSL_CERT_FILE=/etc/ssl/certs/ca-certificates.crt \
    REQUESTS_CA_BUNDLE=/etc/ssl/certs/ca-certificates.crt
Watch out

Setting verify=False, NODE_TLS_REJECT_UNAUTHORIZED=0 or curl -k to make a demo work trains everyone to accept interception and will fail any security review. Fix trust properly, even under time pressure.

Firewalls, egress allowlists and DNS

Inbound and outbound traffic is filtered. Your software may need outbound access to your company's API, a model provider, a container registry or a package index, and the customer's network team must allow each one. They will need precise information: destination hostnames (not "the internet"), ports, protocol, direction, source hosts or subnets, and why. Ask early; firewall change processes can take weeks.

DestinationPortPurposeRequired when
api.yourproduct.example443/TCPProduct API and licence checkAlways (unless fully air-gapped)
registry.yourproduct.example443/TCPContainer image pullsInstall and upgrades
llm.provider.example443/TCPHosted model inferenceIf not self-hosting models
telemetry.yourproduct.example443/TCPOptional usage metricsOnly with customer approval

Split-horizon DNS means the same name resolves differently inside and outside the network, and some internal names only exist on internal DNS servers. A container or pod using a different resolver than the host can fail to find internal services. When in doubt, check resolution from inside the container or pod with getent hosts and compare with the host.

Getting in: VPNs, jump hosts and access

Customers grant access in many forms: a VPN client, a virtual desktop, a bastion (jump) host you SSH through, a cloud console role, or screen-sharing where the customer types. Use exactly what is offered, and do not create side doors such as personal tunnels or reverse shells, even temporarily.

SSH through a jump host without copying keys onto it
bash
# one-off
ssh -J you@bastion.corp.example you@app01.internal.example

# ~/.ssh/config so plain 'ssh app01' works
cat >> ~/.ssh/config <<'EOF'
Host app01
  HostName app01.internal.example
  User you
  ProxyJump you@bastion.corp.example
EOF
  • Prefer short-lived credentials and personal accounts over shared ones, so actions are attributable.
  • Keep a written record of what access you have and request its removal when the engagement ends.
  • Port-forward with ssh -L only for the duration of a task, and only for ports you have been allowed to use.

Single sign-on and how users get in

Enterprise users expect to log in with their company identity, not a new password. The application you deploy should delegate authentication to the customer's identity provider (IdP), such as Microsoft Entra ID, Okta or Keycloak, using OIDC (OpenID Connect, built on OAuth 2.0, common for modern apps) or SAML (older, XML-based, still widespread).

  • You register the application with the IdP and receive a client ID and secret (OIDC) or exchange metadata (SAML), plus a redirect or callback URL you configure exactly.
  • Group or role claims in the token map to permissions in your app; agree the mapping with the customer.
  • Clock skew, redirect URL mismatches and missing claims are the usual first-day errors; the IdP's sign-in logs usually say exactly which.
  • Service-to-service calls use machine identities (client credentials, workload identity, mTLS), not a person's login; the integration lesson covers these.
Hands-on practice

Simulate an enterprise network

  1. Run a forward proxy locally (for example a squid or tinyproxy container) and block direct outbound traffic from a test container with a Docker network that has no default route except through the proxy container.
  2. Make curl and a small Python httpx script work through the proxy using HTTPS_PROXY and NO_PROXY.
  3. Create your own CA with openssl, issue a certificate for a local HTTPS test server, and observe the verification error from your script.
  4. Fix it properly by adding the CA to the container's trust store and setting SSL_CERT_FILE; confirm verification is on.
  5. Write the firewall request you would send a customer for a tool that needs your API, a registry and a model provider.
  6. Configure ProxyJump in your SSH config for a two-hop path between two local VMs or containers.
Cheat sheet

Networks and security at customer sites — at a glance

Main things to focus on

  • Outbound traffic often must use an explicit proxy; internal hosts go in NO_PROXY.
  • Containers and the Docker daemon need proxy settings passed explicitly.
  • Certificate errors on valid sites usually mean TLS inspection: trust the customer CA.
  • Never disable certificate verification to make something work.
  • Firewall requests need exact hostnames, ports, direction, source and reason, early.
  • Delegate user login to the customer's IdP with OIDC or SAML.

Common pitfalls

  • Forgetting NO_PROXY, so internal and in-cluster calls go to the proxy.
  • Disabling TLS verification instead of trusting the customer CA.
  • Asking for 'internet access' instead of specific destinations and ports.
  • Testing DNS on the host when the container uses a different resolver.
  • Creating unofficial tunnels or shared accounts to save time.
