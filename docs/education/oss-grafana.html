Grafana in practice

Data sources, dashboards as code, variables, alerting and provisioning — and how to build an LLM-serving dashboard.

Intermediate ~30 min read Module 6 of 10
Lesson Practice Cheat sheet Quiz

Grafana is where metrics, logs and traces become something a person can read during an incident. The SRE track covered building panels; this lesson looks at Grafana as software you operate, from grafana/grafana: how it is put together, how to run it reliably, how to keep data sources and dashboards in code instead of in someone's browser, how variables make one dashboard serve every service, and how to build a dashboard for an LLM-serving fleet.

After this module you can
  • Describe Grafana's backend, frontend, plugin and database layers
  • Run Grafana with an external database and configuration from environment variables
  • Provision data sources and dashboards from files, or sync them with Git
  • Use template variables, repeats and the right interval macros in queries
  • Build an inference dashboard around latency, throughput, queueing and errors

Inside the repository

Grafana is a Go backend and a React frontend in one repository, licensed AGPL-3.0. pkg/ holds the server: HTTP API, authentication, the alerting engine, query routing and the storage layer. public/app/ is the web application. packages/ publishes the libraries that plugin authors use, such as @grafana/ui and @grafana/data. conf/defaults.ini lists every setting with its default, and conf/provisioning/ shows sample provisioning files.

  • Data source plugins translate Grafana queries into Prometheus, Loki, Tempo, PostgreSQL, Elasticsearch and many more. Grafana stores no metrics itself; it queries the systems that do.
  • Panel plugins draw things: time series, stat, gauge, table, heatmap, logs, traces, node graph.
  • App plugins bundle pages, data sources and dashboards into one installable product.
  • The Grafana database stores users, organisations, dashboards, folders, alert rules and settings. It is SQLite by default; MySQL and PostgreSQL are supported for production and required to run more than one Grafana replica.
Note

Every setting in defaults.ini can be overridden with an environment variable named GF_<SECTION>_<KEY>, for example GF_DATABASE_TYPE=postgres. That is the cleanest way to configure Grafana in containers.

Running Grafana for real

A Grafana on its default SQLite file inside a container loses every dashboard when the pod is rescheduled. For a shared instance, point it at a managed database, run two or more replicas behind a load balancer, and keep secrets out of the config file.

Grafana in Docker with Postgres and admin password from the environment
bash
docker run -d --name grafana -p 3000:3000 \
  -e GF_DATABASE_TYPE=postgres \
  -e GF_DATABASE_HOST=db.internal:5432 \
  -e GF_DATABASE_NAME=grafana \
  -e GF_DATABASE_USER=grafana \
  -e GF_DATABASE_PASSWORD="$GRAFANA_DB_PASSWORD" \
  -e GF_SECURITY_ADMIN_PASSWORD="$GRAFANA_ADMIN_PASSWORD" \
  -v "$PWD/provisioning:/etc/grafana/provisioning" \
  grafana/grafana:13.2.3
  • Pin the image tag; the default port is 3000 and the default login is admin/admin until you change it.
  • Configure SSO (OAuth or SAML) and map identity-provider groups to Grafana teams and roles instead of creating local users.
  • Use service accounts with tokens for automation; personal API keys tied to people break when people leave.
  • Grafana-managed alerting with several replicas needs those replicas to find each other (HA alerting settings), so alerts are not sent twice.

Dashboards and data sources as code

Dashboards clicked together in the UI drift, get deleted, and differ between staging and production. Grafana offers several ways to keep them in version control. The oldest and simplest is file provisioning: YAML files in provisioning/datasources/ and provisioning/dashboards/ that Grafana reads at start-up and, for dashboards, keeps watching.

provisioning/datasources/prometheus.yaml
yaml
apiVersion: 1
datasources:
  - name: Prometheus
    uid: prom-main
    type: prometheus
    access: proxy
    url: http://prometheus.monitoring.svc:9090
    isDefault: true
    jsonData:
      timeInterval: 30s
provisioning/dashboards/files.yaml: load every JSON in a folder
yaml
apiVersion: 1
providers:
  - name: platform
    folder: Platform
    type: file
    allowUiUpdates: false
    options:
      path: /var/lib/grafana/dashboards
      foldersFromFilesStructure: true

Give data sources a fixed uid so dashboard JSON can reference them reliably across environments. Newer options build on the same idea: Git Sync (generally available since Grafana 13) connects a folder to a Git repository two ways, so saving in the UI can open a pull request and merging in Git updates Grafana; the Foundation SDK generates dashboard JSON from Go, TypeScript, Python, Java or PHP; and the gcx CLI pushes resources through Grafana's newer REST APIs from CI. Terraform's Grafana provider remains a good fit if the rest of your stack is Terraform.

Variables: one dashboard for every service

A template variable is a dropdown whose value is substituted into every query on the dashboard. A query variable fills itself from your data, for example label_values(up, namespace) for Prometheus, and variables can chain, so choosing a namespace narrows the list of services. Repeat a panel or row over a multi-value variable to get one per selected model, region or pod.

Panel query using variables and the rate interval macro
promql
sum by (model) (
  rate(inference_requests_total{namespace="$namespace", model=~"$model"}[$__rate_interval])
)
  • Use $__rate_interval in rate() and increase(): it stays at least four scrape intervals wide (from the data source's scrape interval setting), so zooming out never produces empty or jagged graphs.
  • $__interval is the time per data point for the current zoom; good for _over_time functions, not for rate().
  • Use =~ with multi-value variables, because Grafana expands several selections into a regex such as (a|b).
  • Filters (formerly called ad hoc filters) add label matchers to every query without editing each panel.

An LLM-serving dashboard

A good service dashboard answers "is it healthy, and if not, where?" in the top row, then lets you drill down. For an inference fleet built on vLLM or a similar engine, lay it out like this, one row per question, with $model as the repeat variable:

RowPanelsQuery idea
Is it up and fast?Stat: request rate, error ratio, p95 time to first tokenhistogram_quantile(0.95, ...time_to_first_token...)
Is demand outrunning capacity?Time series: requests running vs waitingvllm:num_requests_running, vllm:num_requests_waiting
Is the GPU memory full?Gauge: KV cache usage per podvllm:kv_cache_usage_perc
What does it cost?Time series: prompt and generated tokens per secondrate(vllm:prompt_tokens_total[$__rate_interval])

Add an annotation query for deploys so a latency step lines up visibly with the release that caused it, and link each panel to the matching Tempo traces or Loki logs through data links. Keep it to one screen of headline panels; anything below the fold is for investigation, not for spotting trouble.

Hands-on practice

A provisioned Grafana you can rebuild from Git

  1. Create a folder with provisioning/datasources/prometheus.yaml and provisioning/dashboards/files.yaml from this lesson, plus an empty dashboards/ folder.
  2. Start Prometheus and Grafana with Docker Compose, mounting the provisioning and dashboards folders, and log in on port 3000.
  3. Build a dashboard with a job query variable (label_values(up, job)) and a panel showing rate(prometheus_http_requests_total{job=~"$job"}[$__rate_interval]).
  4. Export it as JSON (Share, then Export), save it into dashboards/, and set allowUiUpdates: false.
  5. Delete the Grafana container and its volume, start it again, and confirm the data source and dashboard come back untouched.
  6. Change the panel title in the JSON file, wait for the provisioner to pick it up, and refresh the browser.
  7. Commit the folder to Git: your monitoring is now reproducible.
Cheat sheet

Grafana in practice — at a glance

Main things to focus on

  • Grafana stores dashboards and settings, not metrics: it queries data sources.
  • Use MySQL or Postgres, not SQLite, for any shared or multi-replica instance.
  • Configure with GF_SECTION_KEY environment variables; manage access with SSO and service accounts.
  • Keep data sources and dashboards in Git: file provisioning, Git Sync, Foundation SDK, gcx or Terraform.
  • Variables plus repeats turn one dashboard into one per service, model or region.
  • Use $__rate_interval inside rate(); headline panels first, investigation below.

Config and ops

GF_DATABASE_TYPE=postgresOverride any defaults.ini key via the environment
GF_SECURITY_ADMIN_PASSWORD=...Set the initial admin password
/etc/grafana/provisioning/{datasources,dashboards}/Where provisioning YAML is read
grafana cli plugins install PLUGIN_IDInstall a plugin on the server
GET /api/healthLiveness and database check endpoint

Provisioning YAML

apiVersion: 1Required header for every provisioning file
datasources: [{name, uid, type, url, access: proxy}]A data source with a stable uid
providers: [{type: file, options: {path: DIR}}]Load dashboard JSON from a folder
foldersFromFilesStructure: trueMirror sub-folders as Grafana folders
allowUiUpdates: falseStop UI edits that would be overwritten

Variables and macros

label_values(METRIC, LABEL)Prometheus query variable values
$__rate_intervalSafe window for rate() and increase()
$__interval / $__rangeStep per point / whole time range
LABEL=~"$var"Match a multi-value variable
${var:csv} / ${var:pipe}Format multi-value variables explicitly

Dashboards as code

Git SyncTwo-way sync of a folder with a Git repository
Foundation SDKGenerate dashboard JSON from code
gcxCLI for Grafana's REST APIs (grafanactl is deprecated)

Common pitfalls

  • Running a shared Grafana on SQLite in a container without persistent storage.
  • Hand-editing production dashboards that are also provisioned, and losing the edits on the next reload.
  • Using a fixed [1m] window in rate() so panels break when someone zooms out to 30 days.
  • Referencing data sources by name in dashboard JSON instead of a stable uid.
  • Dashboards with forty panels and no clear top row, unusable during an incident.
