From field work to product

Spotting patterns across customers, avoiding forks, writing field requests product teams act on, and building reusable components.

Advanced ~35 min read Module 18 of 20
Lesson Practice Cheat sheet Quiz

An FDE team that builds a custom solution for every customer becomes a consultancy with a product attached, and eventually drowns in forks it cannot maintain. The best FDE organisations do the opposite: they treat each deployment as research, notice what repeats across customers, and turn it into product. This lesson covers how to keep customer-specific work thin, structure code as configuration and extensions instead of forks, recognise patterns worth productising, write field requests that product teams act on, and build an internal library of reusable components and playbooks.

After this module you can
  • Explain why bespoke forks are costly and how to avoid them
  • Separate customer-specific configuration and extensions from shared code
  • Recognise patterns across deployments that should become product
  • Write field requests with evidence that product teams can prioritise
  • Contribute reusable components, templates and playbooks to the FDE team

The cost of forks

A fork is a copy of the product's code modified for one customer. It feels fast: change anything, ship today. Then the product releases a security fix and you must merge it into twelve divergent copies, each with its own bugs and its own undocumented behaviour, maintained by whichever FDE happened to write it. Upgrades stall, customers fall behind, and the team's capacity disappears into maintenance.

The goal is that every customer runs the same product version, and everything that differs is expressed in configuration, data, or well-defined extension points. Customer-specific code is allowed, but it lives outside the product, behind stable interfaces, so the product can upgrade underneath it.

This is not an argument against speed. Early in an engagement, a quick customer-specific script is often the right call. The discipline is to keep it outside the core, label it honestly as customer-specific, and revisit it when the next customer needs something similar, rather than letting it quietly become part of a private version of the product.

A connector interface: the product owns it, customers plug in
python
from typing import Iterable, Protocol


class Document(dict):
    """id, text, title, updated_at, acl"""


class Connector(Protocol):
    name: str

    def list_changed(self, since: str) -> Iterable[Document]: ...
    def acl_for(self, doc_id: str) -> list[str]: ...


CONNECTORS: dict[str, type] = {}


def register(cls):
    CONNECTORS[cls.name] = cls
    return cls


@register
class AcmeDmsConnector:                 # lives in the customer's extension package
    name = "acme-dms"

    def list_changed(self, since: str):
        yield from acme_client.documents(modified_after=since)

    def acl_for(self, doc_id: str) -> list[str]:
        return acme_client.permissions(doc_id)

With an interface like this, the second customer with a similar system reuses or adapts a connector instead of patching the core, and the product team can see from the registry which connectors exist and which keep being rebuilt, a strong signal for productisation.

Spotting patterns worth productising

  • The rule of three: the first time, build it for the customer; the second, notice the similarity; the third, propose it as product.
  • Repeated glue: the same integration (a common CRM, document store, ticketing system) built at several customers.
  • Repeated workarounds: scripts or manual steps every deployment needs (data cleanup, permission sync, report exports).
  • Repeated objections: the same security-review question or missing feature blocking several deals.
  • Repeated configuration: the same settings changed from default at every customer, which suggests the default is wrong.
Tip

Keep a shared log across the FDE team: customer, need, workaround used, effort spent. A month of entries turns opinions into a ranked list with evidence.

Field requests that get acted on

Product teams receive many requests and must prioritise. A request that says "customer X wants Y" competes poorly; one that quantifies the need across customers, explains the underlying problem and shows what the workaround costs gets attention.

A field request template
text
Title:        Permission-aware retrieval for SharePoint sources
Problem:      Users must only see answers from documents they can open.
              Today each deployment hand-builds ACL sync (2-3 weeks of FDE time).
Customers:    Acme Insurance (live), Globex Bank (pilot), Initech (blocked in security review)
Evidence:     3 deployments, ~8 FDE-weeks spent on workarounds; Initech deal at risk
Workaround:   Nightly ACL export script per customer (fragile, 24h staleness)
Proposal:     Native ACL sync for the SharePoint connector, filter at retrieval
Not needed:   Real-time sync; field-level permissions
Contact:      FDE lead for Acme, available for design review

Follow up: join the design discussion, offer real data and users for testing, and close the loop with the customers when it ships. FDEs who are known for well-evidenced requests become trusted partners of product teams, and see their requests built.

Building the team's toolkit

  • Reference architectures for common deployment types (cloud SaaS, customer VPC, air-gapped).
  • Templates: discovery summary, pilot plan, status update, security pack, outcome report, runbook.
  • Reusable components: connectors, evaluation harnesses, support-bundle scripts, Helm values for common platforms.
  • Playbooks: step-by-step guides for recurring situations, such as the first week at a new customer or passing a bank's security review.
  • Retrospectives after each engagement feeding all of the above.

Treat the toolkit like product: versioned, owned, reviewed, and pruned when stale. Every hour saved in the next engagement compounds across the team.

Hands-on practice

Refactor a fork into product plus extension

  1. Take a small app you built in this track and imagine three customers, each needing a different document source and different validation rules.
  2. Write the naive version: three copies of the code with customer-specific edits; count the duplicated lines.
  3. Refactor into one core with a Connector interface, a validation hook and per-customer configuration files.
  4. Implement two connectors as plugins and run all three 'customers' from the same core version.
  5. Write a field request using the template for a capability all three needed.
  6. Write one playbook page your team could use at the next customer.
Cheat sheet

From field work to product — at a glance

Main things to focus on

  • Same product version everywhere; differences live in config, data and extensions.
  • Forks feel fast and become a maintenance trap.
  • Interfaces (connectors, hooks) let customer code plug in without patching the core.
  • Rule of three: build, notice, productise.
  • Field requests need cross-customer evidence and the cost of the workaround.
  • Invest in the team toolkit: templates, components, playbooks.

Common pitfalls

  • Copying the product repository per customer.
  • if customer == 'acme' branches in core code.
  • Field requests with one customer's name and no evidence.
  • Productising after one customer, before the pattern is clear.
  • Templates and playbooks that nobody owns or updates.
